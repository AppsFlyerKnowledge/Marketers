> **At a glance:** Последовательность событий в правилах валидации позволяет рекламодателям задавать цепочку событий, которую должен пройти реальный пользователь. Любое отклонение от заданного вами порядка или от интервалов между событиями обнаруживается и блокируется.

<div id="intro" />

## Введение

Рекламодатели могут определить последовательность событий, которую реальный пользователь должен пройти в вашем приложении. AppsFlyer оценивает эту последовательность с помощью окна оценки, которое начинается в день сохранения правила: оно ежедневно увеличивается до 30 дней, а затем становится скользящим 30-дневным окном, которое каждый день сдвигается вперед. События, произошедшие до создания правила, никогда не оцениваются.

Если последовательность нарушается — по порядку или по времени, — пользователь считается поддельным, и:

* Любые события в приложении, а также сессии после прерывания блокируются немедленно.
* Установка блокируется в рамках пост-атрибуции, если она попадает в окно пост-атрибуции (7 дней)
* Связанные события в приложении в пределах окна оценки блокируются в рамках процесса пост-атрибуции
* Другие события в приложении, которые соответствуют условиям правила в других частях приложения, не затрагиваются

Примечание: любое редактирование правила, включая выбор приложения, условий, источника трафика, последовательности событий, а также включение или отключение, сбрасывает окно оценки обратно на день 0.

<div id="who-is-this-for" />

## Для кого это?

Эта функция подходит только для:

* **События SDK** — приложения, в которых будут создаваться правила только со событиями SDK.
* **Неповторяющиеся события** — приложения, в которых есть последовательность событий, где события не происходят более одного раза в этой последовательности. Если одно и то же событие происходит в последовательности более одного раза (например, событие C отправляется дважды), это считается нарушением, и связанные события блокируются.
* **NOI-трафик** — эта функция доступна только для NOI-трафика

## Как настроить правило «Серия событий»

Чтобы настроить правило «Серия событий», выполните следующие действия:

1. Перейдите в **Settings > Validation Rules**
2. Нажмите **+ New rule**
3. Дайте правилу название
4. Откройте вкладку **Post attribution**
5. Выберите приложение, для которого нужно настроить правило  
   Примечание: для каждого правила можно выбрать только одно приложение
6. Определите источник трафика, для которого будет применяться правило
7. Выберите условия. Сейчас доступны следующие варианты:
   1. Гео/страна
   2. Доступно только в <Anchor target="_blank" href="/marketers/ru/docs/about-data-locker-advanced-reports">расширенных отчётах</Anchor>.
8. Уникальный идентификатор задается автоматически в зависимости от выбранного приложения: **IDFA** для iOS или **Advertiser ID** для Android. Вместо этого вы можете использовать **Customer User ID** для любой платформы.
9. Определите последовательность событий: добавьте не менее 2 событий в том порядке, в котором их должен выполнить реальный пользователь
10. При необходимости задайте минимальный интервал времени между каждой парой событий. Если его не задать, по умолчанию применяется минимальное значение — 1 секунда
11. Проверьте раздел **Rule outcome**, чтобы подтвердить состояние окна оценки и минимальное общее время последовательности
12. Нажмите **Сохранить**.

<div id="important" />

> 🚧 **Двоеточие (:)**
>
> Не выбирайте все события приложения. Выбирайте только те события, при которых обычно возможны мошеннические действия.

## Доступ к данным

Когда правило Series of Events блокирует установку или событие в приложении, сведения об этом записываются в отчеты о сырых данных. Перейдите в **Raw Data > Protect360 & Validation Rules**, чтобы найти заблокированные события, и используйте поля ниже, чтобы определить, какие из них были заблокированы этим правилом.

| Отчёт | Ключевые поля |
| --- | --- |
| Пост-атрибуционные установки | <ul><li>Причина фрода = боты валидации</li><li>Подпричина фрода = правила валидации pa</li><li>Значение причины блокировки = название правила</li></ul> |
| Пост-атрибуционные события в приложении | <ul><li>fraud\_reason = боты валидации</li><li>fraud\_sub\_reason = правила валидации pa</li></ul> |
| Заблокированные события в приложении | <ul><li>Причина блокировки = боты валидации</li><li>Подпричина блокировки = правила валидации pa</li><li>Значение причины блокировки = название правила</li></ul> |

## Примеры

Ниже приведены примеры различных последовательностей событий и того, будут ли они считаться фродом или нет.

<Accordion title="Пример 1">

**Определенное правило**

Пользователь должен выполнять события в таком порядке:

* Событие A
* Событие B
* Событие C

**Фактически выполнено**

Пользователь выполняет события в таком порядке:

* День 0: произошла установка
* День 1: отправлено событие A
* День 2: отправлено событие B
* День 3: отправлено событие C

**Результат**

Не фрод. Пользователь выполнил последовательность событий в заданном порядке.

</Accordion>

<Accordion title="Пример 2">

**Определенное правило**

Пользователь должен выполнять события в следующем порядке:

* Событие A
* Событие B
* Событие C

**Фактически выполнено**

Пользователь выполняет события в следующем порядке:

* День 0: произошла установка
* День 1: отправлено событие A
* День 2: отправлено событие C
* День 3: отправлено событие B

**Результат**

Фрод. Пользователь выполнил событие C до события B, что не соответствует заданной последовательности. В результате:

* Событие A будет заблокировано при пост-атрибуции
* Событие B будет заблокировано в реальном времени
* Событие C будет заблокировано в реальном времени или при пост-атрибуции, так как это событие нарушило последовательность
* Все последующие события будут заблокированы в реальном времени

</Accordion>

 Фрод. Пользователь выполнил все события в правильном порядке, но интервал между событиями A и B составил всего 10 минут, что меньше настроенного минимума в 1 час. Временное ограничение было нарушено, несмотря на правильный порядок последовательности. В результате:

* Событие A будет заблокировано при пост-атрибуции
* Событие B будет заблокировано в реальном времени, так как было нарушено минимальное временное ограничение
* Событие C будет заблокировано в реальном времени, так как оно следует за нарушенной последовательностью

<Accordion title="Спецификации и ограничения">

* В каждом правиле можно задать до 100 событий.
* При 80 событиях отображается предупреждение. При 100 событиях лимит достигнут, и правило нужно разделить, чтобы добавить больше событий.
* Минимальное время, которое можно задать между последовательными событиями, — 1 секунда. Если для пары не настроен интервал, автоматически применяется значение по умолчанию — 1 секунда.
* Максимальный конфигурируемый временной интервал между событиями составляет 30 дней и соответствует окну оценки.
* Окно оценки начинается с дня 0 (даты создания правила) и ежедневно увеличивается до 30 дней, после чего становится скользящим 30-дневным окном, которое сдвигается вперед каждый день. События, произошедшие до даты создания правила, никогда не оцениваются.
* Любое изменение правила сбрасывает окно оценки до дня 0.
* Для одной учетной записи можно задать до 10 активных правил.
* Правила для последовательностей событий можно использовать только для неорганического трафика.
* Поддерживается только трафик SDK. Трафик S2S не входит в рамки этапа 1.
* Незавершенные последовательности не помечаются как нарушения.
* Одно и то же событие не может появляться дважды в рамках одной последовательности.
* Между условиями поддерживается только логика AND. Логика OR не поддерживается.

</Accordion>

## Часто задаваемые вопросы

<Accordion title="Что происходит после переустановки?">

Если переустановка сбрасывает события, которые пользователь уже выполнил, это считается нарушением. Если пользователь продолжает с того места, где остановился, нарушение не фиксируется.

</Accordion>
